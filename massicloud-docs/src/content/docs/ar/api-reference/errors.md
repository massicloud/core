جميع استجابات الخطأ تتبع نفس الشكل:

```json
{
  "data": null,
  "error": {
    "message": "وصف مقروء للإنسان",
    "status":  400
  }
}
```

## رموز الحالة الشائعة

| الحالة | المعنى                                                                          |
| ------ | ------------------------------------------------------------------------------- |
| 400    | طلب خاطئ — JSON مشوّه أو حقل مطلوب مفقود                                      |
| 401    | غير مصرّح — مفتاح أو JWT مفقود أو غير صالح                                    |
| 403    | محظور — بيانات اعتماد صالحة لكن RLS رفضت العملية                               |
| 404    | غير موجود — الجدول أو المورد غير موجود                                          |
| 409    | تعارض — انتهاك قيد فريد (مثلًا بريد إلكتروني مكرر عند التسجيل)               |
| 422    | غير قابل للمعالجة — خطأ تحقق (مثلًا كلمة مرور قصيرة جدًا)                    |
| 500    | خطأ داخلي في الخادم — حدث خطأ من جانبنا                                       |

## أخطاء RLS

عندما تحجب RLS عملية، ستتلقى `403` مع:

```json
{ "error": { "message": "row-level security policy violation", "status": 403 } }
```

تحقق من:

1. أن الجدول لديه سياسة مناسبة للدور الطالب
2. أنك تُرسل رأس `Authorization: Bearer` للطلبات الموثّقة
3. أن `auth.uid()` في السياسة يطابق المعرّف الفعلي للمستخدم

## نصائح التصحيح

- `403` على `.select()` يعني عادةً عدم وجود سياسة SELECT لـ `anon`.
- `403` على `.insert()` يعني عادةً أن شرط `WITH CHECK` يفشل.
- `data: []` فارغ (وليس خطأ) يعني أن الاستعلام نُفّذ لكن RLS فلترت جميع الصفوف.
